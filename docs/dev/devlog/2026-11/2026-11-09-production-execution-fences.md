# 2026-11-09 执行入口接入独立恢复隔离

- 日期：2026-11-09
- 范围：`server/cmd/server/`、`server/internal/{chatsession,config,engine,executionlineage,runtime,services,sandbox,payloadhold,envauth}/`，`sandbox-gateway/scripts/test-agent-switching.py` 及其契约测试。
- 做了什么：服务启动先构造独立执行控制，再接入排队、工作流、Solo、PM、定时调度、结果投递、产物和运行时。每次外部证明在 SQL 事务前准备，事务内锁定当前恢复代次、隔离集合及业务父记录后提交；没有有效控制位置的服务仍可读取历史，但不能凭恢复的旧 SQL 自动继续执行。执行器在原操作期限内续期，确定撤权立即取消对应 ACP 操作，不向新占用者发送通用中止。消息、日志、指令及恢复变量的对象读写先释放 SQL，再提交准备好的引用。已标记派发而没有原生结果的旧请求保留待核对状态，不因缺少 transcript 自动重放。保留给平台的运行时身份和私有目录禁止由工作流环境覆盖。
- 为什么：离线恢复工具和控制 schema 本身不能阻止运行中的旧调度器；必须把外部恢复隔离接到实际执行与最终提交入口。对象存储变慢不能同时堵塞这些检查的数据库连接，历史查看也不应变成新的执行许可。首次部署需要显式离线初始化控制位置，普通启动不会自动采用旧数据库中的执行。
- 如何验证：固定源码通过后端 lint、vet、生成配置检查和完整测试；新增当前证明、外层事务边界与撤权拒绝回归后，核心覆盖率达到仓库要求 90.0%。沙箱 lint/vet、96.6% 核心覆盖率与运行时脚本回归、root gate、docs 构建/审计通过。完整 Agent 切换矩阵通过 84 项，覆盖 8 种工具及所有不同工具的有序切换；5 种可配置 CLI 使用原生进程和本地受控模型，Cursor、Trae、Kimi 的专有平台推理保持明确的协议 fixture 边界，付费调用为零。该验证不代表工作区快照的产品 API、目录激活、Return 或显式释放已完成，后续接线另行核验。
