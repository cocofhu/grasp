# 2026-11-09 工作区恢复受理与原回执核对

- 日期：2026-11-09
- 范围：`server/internal/models/workspace_restore.go`，`server/internal/services/workspace_restore*.go`。
- 做了什么：增加独立工作区恢复服务，共用既有快照流水线和任务 worker。受理身份固定原 Solo、快照、预期绑定和客户端 nonce；先核对已受理请求，再检查新的执行条件。新请求核对目标绑定、原快照就绪及来源权限，完整校验对象后分块发送，恢复至运行时可信恢复目录下的专属新目录。只有原生完成回执身份、摘要、数量及目录全部相符，才能在同一事务发布 restored 与任务结果；不自动激活目录。
- 为什么：响应丢失不等于恢复失败，更不能再次解包覆盖后续修改。PUT 或 Finish 结果不明时保留 unknown，显式核对只读取原任务；原请求回执仍可在绑定变化后读取，不能据此再次授权执行。所有构造依赖均需显式提供当前绑定、来源读取权限及执行权准备/事务内核验，无默认放行。公开 HTTP/UI 接线、激活、Return 和释放属于后续模块；此服务证明不代表它们已完成。
- 如何验证：固定源码通过完整后端 lint/vet、配置文档检查、测试、核心 90.1% 覆盖率及运行时重点回归，root gate、docs 构建/审计通过；快照与恢复重点回归 race 三轮通过。真实独立 backend、认证 HTTP、原生 Git、生产传输客户端及对象存储契约 fixture 完成捕获、校验、产品服务受理和隔离目录物化；故意丢弃已确认原生完成后的 Finish 响应，随后只 GET 原回执恢复服务状态，无再次 Create/PUT/Finish。2 MiB 二进制、未推送提交、暂存区和未提交内容一致，来源后续修改、目标原文件及恢复目录内后续修改保留。坏回执、权限撤回、绑定/来源变化、越权重试及完成钩子失败均不能提交成功。
