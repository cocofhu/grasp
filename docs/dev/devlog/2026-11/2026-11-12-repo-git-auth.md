# 2026-11-12（Git 授权改由仓库配置）

- 日期：2026-11-12
- 范围：`server/internal/models/{solo,workflow}.go`、`server/internal/runtime/`（仓库凭据解析、`CloneRepos`、`run_sandbox_env.go`）、`server/internal/engine/{start_run,run_repos}.go`、`server/internal/services/{project,workflow,workflow_import,onboarding,team,agent,shared_agent,sandbox*,solo*}.go`、`server/internal/handlers/{run,workflow,onboarding,shared_agent,dto}.go`、`server/cmd/server/main.go`、`server/openapi.yaml`、`server/internal/sandbox/`（`Spec`、注入包、reprime、worktree）、`server/internal/execution/auth.go`、`sandbox-gateway/sandbox/scripts/{startup,reprime}.sh`、`agents/*/agent.json` 与 `team_embed/*/agent.json`；Web 的 `ProjectForm`、新组件 `RepoCredentialSelect`、`RepoChoiceList`，`WorkflowDefaultsPanel`、`RunLaunchModal`、`AgentChatTester`、`HomeCreateBaselineModal`、`WorkflowsView`、引导与团队向导，删除 `AgentGitCredentialPicker`、`ReposEditor` 和 `repos` 变量类型；文档与对应测试。
- 做了什么：
  - 仓库（Project）新增 `credentialId`、`commitName`、`commitEmail`。保存时校验凭据存在、未吊销，并与地址的协议和主机一致；删除仓库时从工作流绑定里移除。
  - 工作流在 `defaults.repos` 绑定仓库，保存时校验仓库存在、分支合法；导入时丢弃绑定。启动运行可传 `repos` 选子集并改分支，引擎快照到 `Run.Repos`，省略时取全部绑定仓库，cron 和渠道触发同样取全部。
  - 沙箱每次启动按快照仓库实时读取凭据和提交身份：凭据以 `repo:<目录名>` 进入受限 catalog，只对该仓库地址生效；提交身份经新的 `GIT_REPO_AUTHORS` 写入各仓库 `git config`。仓库凭据计入 Git 指纹。运行 env 禁止设置 `GIT_REPOS`、`GIT_REPO_AUTHORS`。
  - 删除 Agent 与默认配置的 `gitBindings`、`inheritGit` 及其解析、UI 和测试；删除 `repos` 变量类型、`${vars.repos}` 标题与解析；内置 Agent 不再声明 `GIT_REPOS`。
  - 删除沙箱的环境变量 Git 回退：`sandbox.Spec` 去掉 `SSHPrivateKey`、`SSHKnownHosts`、`GitBindingsConfigured`，每个沙箱都下发 Git catalog（没有仓库凭据时为空清单），`GITHUB_TOKEN`、`GIT_SSH_PRIVATE_KEY` 等环境变量一律不进沙箱；`execution.Auth` 只认仓库凭据和 catalog，匹配不到即拒绝，不再按主机挑令牌；`startup.sh`、`reprime.sh` 删除暂存目录 `id_rsa` 的应用逻辑。镜像单独运行时读取 `GITHUB_TOKEN` 等变量的入口保留。Git 指纹不再包含 SSH 和“是否配置”两项，已有共享沙箱升级后会 reprime 一次。
  - 引导向导的 Git 步骤改为填写仓库地址、分支、凭据和提交身份，生成时登记为仓库并绑定到默认工作流；团队向导改选一个已登记仓库（`repoId`）。
  - Web：仓库表单增加凭据（只列出与地址匹配的 Git 凭据）和提交身份；工作流设置增加仓库绑定；启动弹窗按绑定仓库勾选子集并改分支；对话测试、从基线新建工作流改为勾选已登记仓库；运行详情显示快照仓库名。仓库勾选列表改用 `AppSwitch`，与设置弹窗其他控件一致。
- 为什么：10 月的设计把凭据挂在 Agent 上、仓库清单靠环境变量引用工作流变量，凭据与仓库要分两处配置并靠 scope 匹配，容易配错。凭据和提交身份本来就是仓库的属性，绑定关系也应属于工作流，这样每处只配一次、含义直接。按要求不做迁移、不留兼容层，CHANGELOG 写明重新配置的步骤。
