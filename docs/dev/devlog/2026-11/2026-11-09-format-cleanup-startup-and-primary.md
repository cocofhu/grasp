# 2026-11-09 清理版在启动前验证格式并移除旧正文读取

- 日期：2026-11-09
- 范围：`server/cmd/server/`、`server/internal/formatguard/`、`historymigration/`、`filestore/`、`blob/`、`payloadstore/`、Solo 历史及队列服务、相关定向测试、`server/UPGRADING.md` 与 `server/STORAGE.md`。
- 做了什么：启动在运行登记、schema 更新、正文目录与远端访问之前，用同一只读 SQL 视图检查真实空库来源或完整规范化收据、当前 typed 引用、导入历史的准确来源与范围、旧 Solo 待执行记录的当前数据集隔离，并核对已完成的物理 primary 凭据。真实全新远端安装重复检查空业务条件后，同事务保存位置和凭据。删除运行时 inline 正文适配、旧 Solo Events 数组读取、旧 Solo 队列导入、启动正文迁移与轮询归档、自动本地提升和远端读取的本地回退。离线转换只在维护所有权和全部实例已停止的约束下解码旧 Events；原始来源、截断提示、未知执行身份、正式 JSON 元数据、图片/二进制类型及非 Solo 排队继续保留。
- 为什么：清理版需要依赖已经验证的格式与真实存储位置，避免直接启动旧库时先修改数据，或使用本地副本掩盖远端缺失。正常新聊天、合法历史删除会改变当前引用集合，不能用升级时的全库摘要相等性阻止这些操作，也不能把执行激活当作格式证明。
- 如何验证：本阶段完整 `go test ./...`、`go vet ./...` 与 golangci-lint（0 issues）通过；filestore/blob/formatguard/historymigration/payloadstore 完整 `-race -count=3` 通过。真实原 v3.2.0 模型生成的 SQLite 与 MySQL 8.4.13 数据经迁移版升级、原 UUID 显式初始化、正常新正文，再以清理版启动并读取原 6,000 条历史、图片和附件通过；直接跳级拒绝前后 SQL 与对象文件 SHA 不变。迁移版真实空库安装新增正文后也通过清理版启动。测试未调用模型、未重放旧请求，原生 MySQL 临时实例已按精确身份清理。物理 primary 在完成凭据前不访问对象、有效凭据不读取历史正文的 SQL-only 回归，以及真正空库首次远端绑定的回归均通过。最终合并公共 Core 后另行运行组合门槛与实际远端认证/新安装验证。
