# 2026-11-09 Solo 消息接收、执行与重试改为数据库权威

- 日期：2026-11-09
- 范围：`server/internal/chatsession/`、`server/internal/models/`、`server/internal/services/solo*.go`、`server/internal/handlers/solo.go`、`server/cmd/server/main.go`、`web/src/lib/solo/`、`web/src/components/solo/SoloSessionPane.vue`、API 类型与客户端、语言包、浏览器回归、`CHANGELOG.md`
- 做了什么：
  - 新增逐条不可变消息意图和接收收据，以消息所属会话、操作者和客户端身份去重；哈希客户端身份避免 MySQL 默认排序规则将大小写或末尾空格不同的身份合并。数据库和正文载荷确认后才允许原生派发，最终回复与终态收据使用同一事务。
  - 队列接收、取出、取消、排序、关闭和终态提交使用同一 SQL 行锁；执行者持可续期占用与全局递增代次。取消监视器和续期协程在下一轮前退出，过时代次、续期失败及迟到原生回调不能发布到新轮。
  - 过期执行按实际派发标记恢复：尚未派发可保留原顺序重试，已经派发则保留不明结果收据，禁止盲目重复外部操作。手动取消在崩溃后仍生效；关闭后退出的执行者可被调和清理，不会令重新启动永久卡住。环境准备暂不可用保留等待请求，只读历史不会唤醒手动停止的环境。
  - 旧 pending 数据逐条导入并保留原始身份与字节，整批成功才移除旧行。坏载荷、缺少父会话和读取失败保留待修复；仅以准确的 turn 身份判断旧回复，不把其他工作流的结果当作本轮完成。中断提示失败后会独立重试，即使队列已经为空。
  - 浏览器为每次发送生成固定身份，丢失确认时保留原请求与附件，显示明确重试入口；收到 HTTP 收据或 WebSocket 确认后认领准确消息，避免同文并发串轮。首条消息接收失败返回明确错误，不再仅记日志却报告创建成功。
- 为什么：原内存 FIFO 整批覆盖 pending 表且只记录持久化错误，可能在失败时仍确认接收；跨实例、断连重试和重启会丢失或重复执行意图。执行占用与派发事实必须由可核验的持久状态决定。
