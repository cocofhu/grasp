# 2026-11-09 聊天事件不可变日志与分页存储基础

- 日期：2026-11-09
- 范围：`server/internal/chatsession/`、`server/internal/models/chat_queue.go`、`server/internal/models/models.go`
- 做了什么：
  - 增加按会话递增的事件序号与不可变分块索引，正文使用现有载荷存储后端。分块提交与序号更新为一个事务，原生输出必须持当前执行所有者；旧所有者、失败写入和父会话验证失败均不能推进游标。
  - 增加连续游标读取，按条数和字节分页；缺块、错误版本、范围/会话/代次不符及坏载荷明确报错，整页失败不返回一个看似完整的部分结果。单帧过大明确拒绝，不报告成功后截断。
  - 增加具有条数/字节背压的输出批写器，区分入内存与已确认提交；Flush/Close 可确认持久化，存储故障保留错误并通知执行者。普通请求取消仍可有界写入最后输出，失去执行所有权不能写入；冻结调用方可复用的缓冲区。增加每条事件的服务端时间与流适配器，保留序号、轮次和执行代次，禁止载荷覆盖这些协议字段。
- 为什么：聊天流需要逐步切换到 SQL 索引与不可变对象正文，消除进程内回放窗口和整条历史数组重写；跨实例、长输出和断连恢复依赖可核验的连续记录。
- 如何验证：超过旧上限的 7,013 条事件经两独立 SQL 连接分页完整回读；包括跨块游标、字节边界、大帧、并发分配、SQL 提交失败、旧执行者、错误/缺失分块、缓冲复用、取消/关闭、慢存储背压及协议元数据伪造回归。真实 MySQL 8.4 两连接游标回读与接管后旧所有者追加拒绝重复 5 次通过；SQLite 关键用例 race 重复 3 次通过。完整 server、vet、lint 0 issues 通过，core gate 90.0%；最终基础存储检查继续记录在后续结果中。

该提交仅是内部基础组件与增量表结构，尚未将 Solo 产品聊天流切换到日志，也未交付历史分页 UI。当前产品仍有原来的进程内流与 6,000 帧上限，下一步必须完成持久化后发布、跨实例订阅、最终消息的日志范围、历史分页接口与界面，并明确旧记录的完整性；因此没有新增对外行为的 CHANGELOG 条目。
