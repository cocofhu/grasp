# 2026-11-09（独立执行世代与离线恢复票据基础）

- 日期：2026-11-09
- 范围：`server/internal/{objectstore,executionlineage,models}/`、`server/cmd/storage-admin/`
- 做了什么：新增独立条件写控制存储、五秒私有外部读取证明、SQL 数据集比对及按来源隔离记录。Local 控制目录和 S3 控制位置必须与 SQL、正文及备份位置分离；真实条件创建和 CAS 探针拒绝不支持的后端。启动探针不初始化执行授权。离线 `execution-init` 先创建不可执行世代，再提交隔离及 SQL 绑定，显式激活；`restore-begin` 必须在导入 SQL 前轮换外部世代并保留维护屏障，`restore-finalize` 核对原票据、正文副本及已提交隔离后才激活。旧 `restore` 名严格作为 finalize 别名，不能跳过票据。隔离仅访问元数据，覆盖十六类待执行来源并保留原正文与未知原生状态。
- 为什么：SQL 中的代次会随数据库恢复一起回滚，不能独自授予旧待执行任务再次运行的权利。对象引用或操作方提供的 JSON 也不能冒充已持久化的外部恢复票据。
- 如何验证：固定独立源码完整 server 测试、vet、lint、配置检查及 runtime 回归通过，server-core 覆盖率 90.1%；三个相关包 race 重复两次通过。真实 SeaweedFS 条件创建、陈旧 CAS 和并发单胜者 race 重复三次通过；实际对象复制与独立 SQL 冷恢复票据流程通过。另验证隔离分页、缺表和缺行拒绝、过期或伪造证明、提交前不得激活、失去响应后原票据确认、命名空间别名及符号链接重叠拒绝。
- 边界：本批提供实际离线 CLI 和基础协议，主服务各执行入口、原生续租与界面审查的生产接线另批完成，不能据此宣布 P6 完整交付。绕过受支持工具直接回滚同一外部世代的原始 SQL，无法仅凭两个相同标记检测；控制位置不能随 SQL 一同回滚。未提供批量重放或删除授权，未宣称本批已完成 MySQL 原生恢复验证。
