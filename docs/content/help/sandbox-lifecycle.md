# 沙箱保存、回收与恢复

设置页只保留一个沙箱空闲时长和一个容量上限。空闲时长只对 E2B 生效，默认在模型回合结束 **6 小时（360 分钟）** 后回收；Docker、Kubernetes 沙箱不会因空闲被保存或释放，进程一直运行，直到手动停止、关闭会话或取消运行。容量上限适用于所有后端和用途，最多同时占用 **15 个**沙箱。工作流并发数单独控制任务调度，不作为沙箱占用数量。

| 行为 | Docker | Kubernetes | E2B |
| --- | --- | --- | --- |
| 空闲到期 | 不回收，环境和进程保持运行 | 同左 | 模型回合已结束且没有排队请求时计时；终端、后台进程、页面和 IDE 访问不算。到期后原生快照暂停 |
| 停止环境 | 保存并校验工作区归档，再删除容器 | 保存并校验工作区归档，再删除 Deployment、Pod、PVC 和专属资源 | 原生快照暂停；保留多份时保存独立快照后释放 guest，不重复文件备份 |
| 再次使用 | 重建环境、恢复最新成功归档、重新建立连接 | 同左 | 从最新成功快照恢复，重新建立连接 |
| 运行中周期备份 | 无 | 无 | 无 |
| 取消运行或关闭会话 | 删除该运行的环境与全部恢复点 | 同左 | 删除 guest 与恢复点，物理磁盘由 provider 回收 |

文件归档保留工作区，排除可重建的 `node_modules`、`.venv`、`__pycache__`、`.cache`、`.pnpm-store`。Docker/K8s 恢复不保留进程内存，工作区以外的临时文件也不在归档内；E2B 保留进程内存，但 TCP 连接和正在进行的外部请求仍会断开。宿主机共享 bind mount 不随 Docker 沙箱删除；K8s 底层卷空间释放由存储类和 CSI 的回收策略决定。

## 等待人工和正在工作的任务

以下空闲计时与「永不自动回收」只适用于 E2B。空闲计时从模型完整回合结束、且没有待执行请求时开始；尚未发起回合的新环境从就绪时开始。模型生成、思考、执行工具或等待工具结果期间都不回收，新回合结束后重新计时。计时保存在数据库里，平台重启后继续有效。页面轮询、WebSocket、IDE/预览访问和终端活动都不续期，所以回合结束后遗留的开发服务器、下载或后台命令，也会随环境在到期后保存并暂停。例外是通过 [SSH 网关](local-ide.md) 连接的本地 IDE：连接期间不会回收，最后一个连接断开后重新计时。

需要长期保留时，在侧栏「正在执行」的会话或运行上右键，勾选 **「永不自动回收」**。该设置保存在会话或运行上，平台重启、环境恢复或重建后继续生效；取消勾选会重新给予完整时长。它仍计入同时运行上限，也不影响手动停止、取消运行和关闭会话。Docker/K8s 环境本来就不会被自动回收，菜单中不显示此项。

工作流等待人工且当前回合已经结束时，E2B 环境可以按统一时长保存并回收，工作流继续保持等待；Docker/K8s 环境在等待期间一直保留。用户回复后，先恢复环境再继续节点。多个节点共享沙箱时，任一节点仍在执行都阻止空闲回收。

手动停止使用同一条保存路径。尚有任务或排队请求时不会强行保存并关闭。取消运行是结束该运行并清理数据的独立操作，会保留对话/流程历史，但不再保留该运行的环境恢复点。

## 恢复点数量与失败处理

## E2B 空闲内存归还

E2B 沙箱读过的文件会留在沙箱内的页面缓存里，空闲内存也会碎成小块，主机的大页池因此无法收回这些内存，新沙箱可能因池内空间不足而创建失败。模型回合结束 10 分钟后，Grasp 会在沙箱内写盘、清理文件缓存并整理内存碎片，空闲内存随后整块还给主机；之后持续空闲时每 30 分钟检查一次，缓存超过 1 GiB 才再次清理，开启「永不自动回收」的环境也照常执行。这不会丢数据，也不会中断进程，只是下一次编译或打开大项目时需要重新读盘，第一次会稍慢。Docker/K8s 容器与宿主机共用内核，不执行此操作。

```yaml
sandbox:
  idle_ttl_minutes: 360
  memory_trim_idle_minutes: 10 # 负数关闭
  memory_trim_interval_minutes: 30
  memory_trim_min_cache_mb: 1024
  max_sandboxes: 15
solo_backup:
  keep: 1
```

`solo_backup.keep` 同时控制文件归档与 E2B 的成功恢复点数量，默认 1，可配置为更大正数。名称沿用现有配置，作用于全部沙箱。新保存成功后才淘汰旧版本；恢复始终选择最新成功版本，不提供版本选择，也不会在最新归档损坏时悄悄回退。现有归档保留引用并迁入统一记录，不作为无用历史直接删除。

E2B 默认 `keep: 1` 使用原生暂停/恢复，保留多份时用官方独立快照接口保存，成功后释放源 guest 并淘汰超出数量的旧点。恢复优先连接原 guest，只有它明确不存在时才使用最新保存对应的独立快照。此时 provider ID 会变，Grasp 中的沙箱身份不变。多份保留增加存储和保存时间，不增加运行中的周期备份。

文件备份、校验失败时不删除原工作负载。E2B 遵循官方暂停和快照的可恢复性合同，保存失败不淘汰旧点；Grasp 不额外等待私有的上传/进程退出证明。存储故障与物理回收由 provider 处理，不保证未持久化数据能抵抗断电。

删除失败会保存清理意图并重试。E2B 快照可能引用旧层，正在使用的快照、模板和 guest 引用的层不会删除，因此 `keep: 1` 不等于磁盘上只有一个文件。VM 已确认释放后不再占运行名额，剩余磁盘回收继续跟踪；不能只因控制面不再展示 guest 就认为磁盘已释放。

## 升级与运维

升级会一次性迁移数据库中的旧分类容量设置，取较大值；已明确配置的新全局值优先。旧分类 TTL、最长保留、手动续期、周期备份间隔与恢复版本接口移除。配置文件改用上述字段，设置页保存的值优先于 YAML 默认值。降低上限不关闭正在工作的沙箱，只阻止超过配额的新建和恢复。

标准 E2B 不需要私有扩展或定制 Dashboard。启用多份保留前须验证 provider 支持官方独立快照接口；不支持时会保存失败，不静默降为一份。已有自建增强部署先更新负责标准接口存储回收的 API 与迁移，再更新 gateway 和 Grasp。单节点 orchestrator 升级应安排无业务任务的维护窗口；测试使用独立沙箱，不能停止或删除业务沙箱来验证回收。具体合同见 [E2B 部署说明](https://github.com/cocofhu/grasp/blob/main/sandbox-gateway/deploy/e2b/README.md)。
